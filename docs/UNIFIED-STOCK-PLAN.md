Статус (25.10.2026): этапы 1, 1б, 2, 3 и 4 сделаны локально — все склады (одежда, ручки, блокноты, кружки, рулоны, бумага, расходники принтеров) работают на едином складе. Этап 5: уборка кода сделана, удаление старых таблиц подготовлено в `docs/cleanup/` (после месяца работы). Осталось: применить его и этап 6 (сайт). Не закоммичено и не выкачено.

Парк оборудования: широкоформатный принтер, UV, DTF, Ricoh C5200 (тонер) — по одному.

## 1. Зачем

Сейчас каждый вид товара живёт в своём «мини-складе». Добавить новую категорию (носки, боди, худи) или новый принтер (Ricoh C5200, второй UV) — это новые таблицы, API, страница и правки в заказах, e-Factura и прибыли. Цель — **один механизм**: любая позиция заводится в админке как данные, а приход, списание, себестоимость, закупки и (позже) витрина для клиентов работают одинаково для всех.

## 2. Как устроено сейчас (факты из кода)

| Что | Где хранится | Особенность |
|---|---|---|
| Кружки, блокноты, ручки | `MugProduct` / `NotebookProduct` / `PenProduct` + по 2 таблицы приходов и движений | Одинаковая логика, скопирована 3 раза |
| Майки (DTF) | `GarmentProduct` → `GarmentVariant` (размеры) + приходы/движения | Единственное место с вариантами |
| Плёнка и порошок DTF | `DtfConsumableStock` (строки `dtf_film`, `dtf_powder`) | Отдельный «мини-склад» внутри DTF |
| Чернила | `InkInventory` — 3 строки: `large_format_roll`, `uv_rigid`, `dtf_textile` | Один общий объём в мл на **технологию**, без цветов, принтеров и поставщиков |
| Рулоны | `LargeFormatMaterial` + приходы/движения | Единица — погонный метр, свои цены за печать |
| Листовая бумага | `SheetPaper` + приходы/движения | Единица — лист |
| Нормы DTF | `DtfPrintPreset`, настройки DTF | Нормы есть только у DTF |

Итого **8 видов × 3 таблицы ≈ 24 таблицы** с одинаковым смыслом. Следствия в коде:

- `OrderLine` имеет отдельную колонку и снимок под каждый вид (`mugProductId`, `penProductId`, `largeFormatMaterialId`, `sheetPaperId`, `dtfLineData`…).
- `PurchaseInvoiceLine` имеет отдельную связь на приход каждого вида; `recordStockReceipt` в `src/lib/purchasing/stockTargets.ts` — большой `switch` по видам.
- Списание при создании заказа, возврат при удалении и повторное списание при восстановлении расписаны по видам в `src/app/api/orders/route.ts` и `src/app/api/orders/[id]/restore/route.ts`.
- `Order.procurementMeta` («надо докупить») — тоже отдельный вариант под каждый вид (`src/lib/orderProcurement.ts`).
- Деньги хранятся по-разному: у кружек/ручек `Decimal`, у рулонов, бумаги и чернил — целые леи (`Int`).
- `printProcessForProductType` (`src/lib/printProcess.ts`) отправляет визитки, флаеры и бумажную печать в чернила **UV** — для Ricoh это будет неверно.

Что уже хорошо и сохраняется: средневзвешенная себестоимость, приходы из e-Factura с правилами сопоставления, снимки себестоимости в строках заказа (прибыль не «плывёт» задним числом), список «надо докупить».

## 3. Целевая модель

Четыре понятия вместо восьми видов.

### 3.1 Позиция склада и её варианты

```prisma
model StockCategory {          // «Майки», «Носки», «Кружки», «Рулоны», «Чернила», «Тонер»…
  id         String  @id @default(uuid())
  code       String  @unique   // tshirts, socks, mugs, roll_media, ink, toner…
  kind       String            // product | material | consumable
  nameRo     String
  nameRu     String
  nameEn     String
  unit       String            // pcs | m | ml | g | sheet
  sortOrder  Int     @default(0)
  isActive   Boolean @default(true)
  items      StockItem[]
}

model StockItem {              // «Футболка Gildan 64000 чёрная», «Баннер 440 г 3,2 м», «Чернила Epson Cyan»
  id            String   @id @default(uuid())
  categoryId    String
  sku           String   @unique
  nameRo        String
  nameRu        String
  nameEn        String
  imageUrl      String?           // catalog/... (постоянный бакет)
  attributes    Json              // по категории: цвета кружки, ширина рулона, плотность бумаги, цвет чернил…
  isSellable    Boolean  @default(false)  // показывать клиентам (будущая витрина)
  printProfileId String?          // зона печати / DPI / 3D-превью для изделий
  isActive      Boolean  @default(true)
  sortOrder     Int      @default(0)
  legacyKind    String?           // откуда перенесено: mug | pen | garment | …
  legacyId      String?           // id в старой таблице (для сверки и обратных ссылок)
  variants      StockVariant[]
  @@unique([legacyKind, legacyId])
}

model StockVariant {           // размер/цвет; у кружки ровно один вариант
  id              String   @id @default(uuid())
  itemId          String
  sku             String   @unique
  label           String?          // "M", "XL", "чёрный / M"
  options         Json             // { size: "M", color: "black" }
  stockQuantity   Decimal  @db.Decimal(14, 3)   // в единицах категории
  avgCost         Decimal? @db.Decimal(14, 4)   // MDL за единицу, средневзвешенная
  sellPrice       Decimal? @db.Decimal(12, 2)
  dealerPrice     Decimal? @db.Decimal(12, 2)
  priceTiers      Json?            // тиражные цены (как у маек сейчас)
  reorderLevel    Decimal?         // «пора докупать»
  sortOrder       Int      @default(0)
  isActive        Boolean  @default(true)
}
```

**Остаток и себестоимость всегда живут на варианте.** Кружка, ручка, рулон, литр чернил — позиция с одним вариантом. Майка — позиция с вариантами по размерам.

### 3.2 Один приход и одно движение для всех

```prisma
model StockLocation {          // пока одна запись «Основной» (решение по вопросу 6)
  id        String  @id @default(uuid())
  name      String
  isDefault Boolean @default(false)
  isActive  Boolean @default(true)
}

model StockReceipt {
  id                    String   @id @default(uuid())
  variantId             String
  locationId            String           // «Основной» по умолчанию
  quantity              Decimal  @db.Decimal(14, 3)
  totalCostMdl          Decimal  @db.Decimal(14, 2)
  amountsIncludeVat     Boolean
  isProvisional         Boolean  @default(false)
  purchasedAt           DateTime
  supplierIdno          String?          // Inprint, X-Service… — поставщик на приходе, не отдельная позиция
  supplierName          String?
  purchaseInvoiceLineId String?  @unique // связь с e-Factura
  note                  String?
  createdById           String?
  createdAt             DateTime @default(now())
}

model StockMovement {
  id            String   @id @default(uuid())
  variantId     String
  locationId    String                        // «Основной» по умолчанию
  delta         Decimal  @db.Decimal(14, 3)   // + приход/возврат, − расход
  kind          String   // RECEIPT | ORDER_SALE | ORDER_RETURN | PROCUREMENT_BACKLOG | ADJUSTMENT | WRITE_OFF | TRANSFER
  costMdl       Decimal? @db.Decimal(14, 2)   // себестоимость этого движения
  sellPriceMdl  Decimal? @db.Decimal(14, 2)
  orderId       String?
  orderLineId   String?
  receiptId     String?
  note          String?
  createdById   String?
  createdAt     DateTime @default(now())
  @@index([variantId, createdAt])
  @@index([orderId])
}
```

- Деньги — везде `Decimal` (конец смеси `Int`/`Decimal`).
- `StockVariant.stockQuantity` — кэш, источник правды — сумма `StockMovement`. Ночная проверка сверяет их и пишет расхождения.
- Список «надо докупить» — это движения `PROCUREMENT_BACKLOG` (как сейчас), без отдельного варианта под каждый вид.

### 3.3 Оборудование и его расходники

```prisma
model Printer {                // Epson широкоформат, UV, DTF, Ricoh C5200…
  id          String  @id @default(uuid())
  name        String
  technology  String           // roll_solvent | uv | dtf | toner_laser | …
  isActive    Boolean @default(true)
  slots       PrinterSlot[]
}

model PrinterSlot {            // «Cyan», «Magenta», «White», «Плёнка», «Порошок», «Тонер K»
  id         String  @id @default(uuid())
  printerId  String
  label      String
  variantId  String            // какая позиция склада сейчас стоит в этом слоте
}
```

Чернила, тонер, плёнка и порошок становятся обычными позициями (категории «Чернила», «Тонер», «DTF-расходники»). Принтер говорит, **какие** позиции он ест. Смена поставщика краски для Ricoh (X-Service → Inprint) — это просто приходы от другого поставщика той же позиции; если краска физически другая — новая позиция и смена позиции в слоте.

### 3.4 Технологии печати и нормы расхода

```prisma
model PrintTechnology {        // DTF, UV, широкоформат, лазер/тонер
  id        String @id @default(uuid())
  code      String @unique
  name      String
  printerId String?            // принтер по умолчанию
  norms     ConsumptionNorm[]
}

model ConsumptionNorm {        // «DTF: порошок 120 г/м²», «Широкоформат: чернила 10 мл/м²», «Ricoh: тонер 0,05 г/лист»
  id            String  @id @default(uuid())
  technologyId  String
  slotLabel     String?          // к какому слоту принтера относится
  variantId     String?          // или конкретная позиция (плёнка, порошок)
  basis         String           // per_m2 | per_linear_m | per_sheet | per_piece
  amount        Decimal @db.Decimal(14, 4)
}
```

Строка заказа говорит «технология X, площадь/метры/листы/штуки Y» — система сама считает расход по нормам и пишет движения. Сегодняшняя логика DTF (`dtfLineCalc`) и расчёт чернил широкоформата становятся частными случаями этого.

### 3.5 Строка заказа

`OrderLine` получает общие поля, старые колонки остаются до конца переноса:

```prisma
  stockVariantId   String?   // изделие/материал, из которого делаем
  technologyId     String?   // как печатаем
  stockSnapshot    Json?     // sku, название, себестоимость на момент заказа — для прибыли
```

Расчёт цены и раскладки (широкоформат, DTF-плёнка, визитки) **не трогаем** — меняется только то, откуда берутся позиция, остаток и себестоимость.

### 3.6 Будущая витрина

Читает `StockItem` с `isSellable = true`, его варианты с остатком > 0, фото и `printProfile` (зона печати, DPI, 3D-превью — сейчас это поля `printWidthCm/printHeightCm/printDpi/has3dPreview` у кружек и ручек). Отдельного каталога для сайта не нужно.

## 4. Что меняется в экранах

| Экран | Сейчас | Станет |
|---|---|---|

| **Категория** (майки, кружки, рулоны…) | Своя страница на каждый вид | Одна общая таблица позиций: фото, SKU, название, остаток, себестоимость, цены, активна; фильтр и поиск. Поля формы — общие + атрибуты категории |
| **Позиция** | Модалка в каждой странице | Общая карточка: варианты (размеры), история движений, приходы, кнопка «Приход», «Списать/скорректировать» |
| **Принтеры** | Нет | Список принтеров; у каждого слоты с остатками («Cyan — 420 мл, хватит примерно на 40 м²») |
| **Технологии и нормы** | Только внутри DTF | Одна страница: технология → нормы расхода и прайс-пресеты (DTF-пресеты переезжают сюда) |
| **DTF-печать** | Изделия + расходники + прайс в одном | Майки → категория «Майки», плёнка/порошок → расходники DTF-принтера, прайс и нормы → «Технологии» |
| **Чернила** | 3 бака по технологиям | Исчезает как отдельный раздел — чернила видны в «Принтерах» и как категория |
| **Закупки (e-Factura)** | Выбор «вида» + позиции | Выбор одной позиции/варианта из общего поиска; правила сопоставления указывают на вариант |
| **Новый заказ** | Пикеры по видам | Те же шаги; пикер изделия ищет по общему каталогу, но фильтрует по подходящей технологии |
| **Прибыль** | Себестоимость из снимков по видам | Из `stockSnapshot` строки; старые заказы — из старых снимков (ничего не пересчитываем) |

Названия разделов берутся из `StockCategory` — это продолжение «одного источника правды», начатого в `t.admin.stockSections`.

#### Как этап 2 сделан на самом деле (25.10.2026)
- Миграции `20261025160000_unified_stock_printers` и `20261025161000_stock_qty_precision`.

### Этап 3. Изделия (≈1–2 недели, по одному виду за раз)
Порядок: ручки → блокноты → кружки (майки уже перенесены на этапе 1б) (от простого к сложному, кружки последними — у них больше всего заказов и дизайн-студия).
Для каждого вида:
1. Скрипт переноса (раздел 6) на копии прод-базы, сверка остатков и себестоимости.
2. Новые заказы пишут `stockVariantId` + `stockSnapshot` и списывают через `ledger.consume()`.
3. Восстановление/удаление старых заказов: если строка без `stockVariantId` — находим вариант по `legacyKind/legacyId`.
4. Старая страница раздела → редирект на категорию.

## 6. Перенос данных

Каждый перенос — отдельный идемпотентный скрипт `scripts/stock-migrate/<вид>.ts`, который можно запустить повторно (поиск по `legacyKind + legacyId`).

| Старое | Новое |
|---|---|
| `MugProduct` / `PenProduct` / `NotebookProduct` | `StockItem` (категория по виду) + 1 `StockVariant`; цвета/зона печати → `attributes` / `printProfile` |
| `GarmentProduct` → `GarmentVariant` | `StockItem` = модель (категория по `kind`; строки с одинаковым `name` и разным цветом склеиваются) → `StockVariant` на каждую пару цвет + размер; `priceTiers` → вариант |
| `LargeFormatMaterial` | `StockItem` «Рулоны» + 1 вариант (единица м) |
| `SheetPaper` | `StockItem` «Листовая бумага» + 1 вариант (единица лист) |
| `InkInventory` (3 строки) | 3 позиции «Чернила …» + слоты соответствующих принтеров |
| `DtfConsumableStock` (2 строки) | 2 позиции «DTF-расходники» + слоты DTF-принтера |
| `*StockReceipt` | `StockReceipt` (суммы → `Decimal`, `purchaseInvoiceLineId` сохраняется) |
| `*StockMovement` | `StockMovement` (kind сохраняется, `orderId/orderLineId` сохраняются) |
| `SupplierItemMapping.targetKind/targetId` | те же поля: `targetKind = "stock_variant"`, `targetId` = id варианта |
| `PurchaseInvoiceLine.postedKind/postedTargetId` | те же поля; приход находится по `StockReceipt.purchaseInvoiceLineId` |

Проверки после каждого скрипта (и в тестах):
- остаток варианта = старый остаток = сумма перенесённых движений;
- средняя себестоимость совпадает до копейки;
- число приходов и движений совпадает, суммы по месяцам совпадают;
- прибыль за последние 12 месяцев на странице «Прибыль» не изменилась.

Перенос сначала на локальной копии прода, потом на проде в нерабочее время с дампом до и после.

## 7. Риски и как их закрываем

| Риск | Мера |
|---|---|
| Прибыль старых заказов изменится | Прибыль читает снимки на строке заказа; старые снимки не трогаем, новые пишутся в `stockSnapshot` |
| Двойное списание в переходный период | Каждый вид переключается одним флагом; строка заказа списывает либо по старому, либо по новому пути, не оба |
| Расхождение остатков | Остаток — кэш суммы движений; ночная сверка и отчёт расхождений |
| Сложная логика широкоформата | Не переписываем расчёт и раскладку, меняем только источник остатка и себестоимости |
| e-Factura автопроводки | Правила сопоставления переносятся скриптом; до переноса вида правила указывают на старые таблицы |
| Роли | Склад: workshop + superadmin (как сейчас), закупки: только superadmin |

## 8. Открытые вопросы

1. **Ricoh C5200**: это Ricoh Pro C5200s (сухой тонер)? Учитываем тонер в граммах или картриджах? Нужен ли учёт счётчика отпечатков (click charge по сервисному договору)?
   - ✅ **Решение:** тонер учитываем **в картриджах** — 4 позиции категории «Тонер» (C, M, Y, K), единица «шт». Норма расхода — ресурс картриджа в листах (`ConsumptionNorm.basis = per_sheet`, `amount = 1 / ресурс`), себестоимость листа считается по ней. Сервисный договор (клик) не используем.
2. **Чернила по цветам**: достаточно одного общего объёма на принтер (как сейчас на технологию) или нужен учёт по каждому цвету? По цветам точнее, но каждый приход надо будет раскладывать по цветам.
   - ✅ **Решение:** **по цветам** — отдельная позиция на каждый цвет каждого принтера (C, M, Y, K, White, лак…), каждая в своём слоте `PrinterSlot`. Норма на технологию задаёт общий расход в мл, а доли по цветам — в норме слота (по умолчанию поровну, White/лак — своей нормой). На этапе 2 текущие 3 общих бака переносятся как стартовый остаток, разложенный по цветам поровну, с пометкой в движении `ADJUSTMENT`; после первой инвентаризации остатки правятся вручную.
3. **Второй UV-принтер**: общие чернила с первым или раздельный учёт?
   - ✅ **Решение:** UV-принтер один. Парк: **4 принтера — широкоформатный, UV, DTF, Ricoh** — по одному на технологию, у каждого свои расходники в своих слотах. Модель `Printer` всё равно оставляем (а не «технология = принтер»), чтобы второй принтер той же технологии добавлялся данными.
4. **Майки/носки/боди**: какие атрибуты варианта — только размер или размер + цвет внутри одной позиции? (Сейчас цвет — это отдельная позиция.)
   - ✅ **Решение:** **модель → цвет + размер**. Позиция = модель («Футболка Gildan 64000»), вариант = цвет + размер (`options: { color, colorHex, size }`). Фото — на позиции и (по желанию) на цвете. При переносе строки `GarmentProduct` с одинаковыми `kind` + `name` и разными `colorName` склеиваются в одну позицию; если склейка неочевидна, скрипт выводит список на ручное подтверждение. Тиражные цены (`priceTiers`) — на варианте, но редактируются сразу для всех вариантов модели.
5. **Витрина**: цены для сайта = розничные цены варианта или отдельный прайс? Оплата онлайн или как сейчас?
   - ⏸ **Отложено до этапа 6.** На структуру склада не влияет: если понадобится отдельная цена для сайта, это одно поле на варианте.
6. **Склады-локации**: всё в одном месте или будет второй склад/точка (тогда в `StockMovement` нужно поле `locationId` с самого начала)?
   - ✅ **Решение:** сейчас одно место, но **закладываем**: таблица `StockLocation` с одной записью «Основной», обязательный `locationId` в `StockReceipt` и `StockMovement` (по умолчанию «Основной»). В экранах локация не показывается, пока она одна. Остаток на варианте — сумма по всем локациям.
